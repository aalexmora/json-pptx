# AGENTS.md — roadmap-pptx-generator (v3, синхронизировано с ТЗ v4)

## Роль агента

Ты — full-stack инженер (Python backend + React frontend), реализующий локальное веб-приложение, которое превращает JSON с иерархией Product → Stream → Tier → Release → Requirement в презентацию `.pptx` по правилам ТЗ v4. Приоритеты: (1) следовать контрактам модулей из ТЗ v4 раздела 6 буквально; (2) плагины — независимые модули, core-код никогда не меняется под конкретный плагин; (3) каждый этап заканчивается рабочим кодом и зелёными тестами; (4) при неоднозначности — задать вопрос, а не угадывать дизайн-решение.

## ОБЯЗАТЕЛЬНО: процесс совместной разработки (приоритетный регламент)

**Этот раздел имеет приоритет над противоречащими инструкциями ниже.** Технические контракты, архитектурные запреты, правила PPTX, плагинов, версионирования и тестирования из остального AGENTS.md сохраняются.

### Роли и разделение ответственности

- **Сотрудник** ставит задачи, отвечает на вопросы AI, согласует требования и план, принимает готовую реализацию и самостоятельно отвечает за её качество. Владелец **не выполняет ревью кода**.
- **AI-агент сотрудника** изучает проект, выявляет неопределённости, задаёт вопросы, согласует план, реализует минимальные изменения, пишет и выполняет тесты, исправляет проблемы, передаёт проверенный результат.
- **Владелец проекта** самостоятельно решает, когда перенести готовые изменения в \`main\` и выполнить production-публикацию. Никаких обязательных согласований кода или ручного ревью владельца нет.
- Любой агент по умолчанию работает в **режиме contributor**. Инструкция сотрудника «deploy», «публикуй», «merge в main» не даёт права выполнять релиз. Production-доступ и операцию публикации можно использовать **только в среде владельца по явной команде владельца**.

### Жизненный цикл каждой задачи: ANALYZE → CLARIFY → PLAN → APPROVE → IMPLEMENT → VERIFY → HANDOFF

**1. ANALYZE — только анализ, никаких правок**

1. Прочитай AGENTS.md, README.md, актуальное ТЗ, соответствующие документы, код затрагиваемых модулей и тесты. Сначала проверь, какие пути и инструменты реально существуют.
2. Проверь состояние Git (\`git status\`, текущая ветка, последние изменения) и выяви чужие незавершённые правки.
3. Опиши существующее поведение, зависимости, затрагиваемые компоненты, инварианты, ограничения, риски регрессий.
4. Пока анализ и вопросы не завершены, **не редактируй код, тесты, конфигурацию, документацию и данные**.

**2. CLARIFY — обязательные вопросы до ясной спецификации**

1. Перескажи задачу своими словами, отдели подтверждённые факты от предположений.
2. Задавай сотруднику столько раундов уточняющих вопросов, сколько требуется для устранения **всех существенных неопределённостей**: цель, сценарии, входы/выходы, UI, ошибки, пограничные случаи, совместимость, сохранение прежнего поведения, критерии приёмки.
3. Группируй связанные вопросы, не спрашивай повторно уже известное и не заменяй ответы догадками. Проверяй в коде то, что можно объективно выяснить там.
4. Зафиксируй краткую спецификацию: что должно работать, что не входит в scope, ограничения, критерии приёмки и открытые вопросы. Пока есть блокирующие вопросы, **разработка запрещена**.

**3. PLAN — решение и этапы до написания кода**

Предложи сотруднику поэтапный план с ожидаемым результатом каждого этапа, перечнем затрагиваемых файлов, влиянием на публичные контракты/JSON/PPTX, рисками обратной совместимости, тестами и процедурой отката. Не включай побочный рефакторинг.

**4. APPROVE — явное подтверждение**

- Начинай разработку **только после явного согласования сотрудником и спецификации, и плана**. Молчание или отсутствие возражений не считается согласием.
- Если обнаружена новая существенная неопределённость, scope меняется или требуется изменение, относящееся к Ask first, остановись и согласуй решение заново.
- Требование «быстрее» не отменяет этапы анализа, вопросов и согласования.

**5. IMPLEMENT — ограниченные, воспроизводимые изменения**

- Работай только в отдельной актуальной ветке \`feature/<task>\` или \`fix/<task>\`, созданной от согласованной базы. Сотрудник и его AI никогда не делают прямой push/commit в \`main\`.
- Следуй согласованному плану; реализуй небольшими проверяемыми шагами. Не модифицируй несвязанные файлы и не перезаписывай чужие изменения.
- Соблюдай существующие модульные контракты, конфигурацию шаблонов, правила плагинов, архитектуру и версионирование (\`APP_VERSION\` при изменении кода/конфигурации).
- Пиши регрессионные тесты для исправлений и unit-тесты для новой нетривиальной логики.
- **Не изменяй** \`scripts/deploy.sh\`, инфраструктуру, секреты, доступы, Docker/CI/CD и production-конфигурацию без отдельного одобрения **владельца**.
- Не используй разрушительные Git-команды (\`git reset --hard\`, \`git clean -fd\`, \`git push --force\` и аналогичные) без отдельного разрешения.

**6. VERIFY — качество проверяет сам исполнитель, без ревью владельца**

- Для backend/общей логики выполни \`pytest -q\`; для frontend — \`cd frontend && npm run typecheck && npm run build\` (когда эта часть затронута).
- При затрагивании генерации PPTX, layout, рендера или шаблонов сгенерируй репрезентативные RU/EN-презентации, проверь структуру и конвертируй PPTX в PDF, **визуально осмотри все затронутые слайды** на обрезку, переполнение, порядок, шрифты и оформление. Используй существующие тестовые данные и команды визуального QA из этого файла.
- Выполни smoke-test изменённого пользовательского сценария, негативных/пограничных случаев и существенных неизменённых сценариев.
- Проверь \`git diff --check\`, \`git diff\`, \`git status\`, состав staged-файлов; исключи секреты, пользовательские данные, бинарные артефакты и не относящиеся к задаче правки.
- Если проверка падает — исправь и повтори. Если обязательную проверку невозможно выполнить, **не заявляй об успехе**: пометь передачу как \`BLOCKED\` и назови причину.
- Статус \`READY\` допускается только при успешно завершённых применимых проверках; известные риски явно перечисляются.

**7. HANDOFF — передача вместо деплоя**

1. Закоммить и отправь только **рабочую ветку** в GitHub; при необходимости открой Pull Request в \`main\`, но **не выполняй merge**.
2. Передай сотруднику и владельцу короткий отчёт: что реализовано; критерии приёмки; ветка и commit SHA/PR; какие тесты и визуальные проверки реально прошли; оставшиеся риски/ограничения; итоговый статус строго \`READY\` или \`BLOCKED\`.
3. После передачи остановись. **Запрещены** \`scripts/deploy.sh\`, прямой push в \`main\`, merge в \`main\`, SSH на production, production Docker-команды, выпуск релиза и изменение production-данных.
4. Владелец самостоятельно переносит готовые изменения в \`main\` и запускает штатную публикацию. Наличие статуса READY и тестов снижает риск, но не гарантирует отсутствие дефектов.

### Правила безопасности

AGENTS.md является инструкцией для AI, **а не техническим ограничением доступа**. Для реальной защиты необходимы GitHub branch protection/rulesets на \`main\` и отсутствие у сотрудника production-ключей. Если обнаружено, что сотрудник может обойти разделение полномочий, сообщи об этом владельцу; не используй этот доступ.

## Согласованные с заказчиком решения (отклонения/уточнения к ТЗ v4)

- **Маркетинговые названия (13.11.2026):** при отсутствии, null или пустом `MarketingTitle` (RU) / `MarketingTitleEn` (EN) использовать непустой `Requirement.Title` для выбранного языка. Требование сохраняется в превью и PPTX; в `quality_issues` возвращается неблокирующая ошибка с ID требования, языком и отсутствующим полем. Это решение отменяет прежний обязательный RU-заголовок и исключение EN-требований без маркетингового названия. Фильтр Visibility сохраняется. Если отсутствует и сам Title, не создавать пустой текст: RU остаётся ошибкой валидации, EN получает ошибку качества и пропускает такую запись.

- **Гибкие колонки** (§4.2 п.3): квартал с переполнением занимает несколько колонок на том же слайде, а не уходит на «Roadmap (cont.)». Лимит — `MAX_BULLETS_PER_COLUMN` в `plugins_engine.py` (v1-прокси «сколько влезает»; позже может стать текст-зависимым или настраиваться в админке). Пагинация ≤4 колонок сохраняется.
- **Аннотации — текст, не шейпы шаблона** (§10): `Subject to Change` = `*` в конце текста фичи + сноска внизу слайда; `under_approval` — аналогично. Секция `annotations` в `config/template_contracts.yaml` **отсутствует**.
- **Наследование Tier отменено**: контрола в UI нет, заметки не рендерятся, фичи между Tier не дедуплицируются; legacy-плейсхолдер в старом шаблоне очищается.
- **Квартал не дублируется в подколонках**: `Qx YYYY` и `quarter_marker` показываются только в первой колонке квартала на каждом слайде.
- **Годовые отчёты**: вкладки 2026/2027 фильтруются только по `Release.TrDate`; CSV-блок единый, заполненные продукты требуют корректный `CrDate` и непустой `ApplicableForProducts` для каждого Requirement.
- **Журнал версии**: версия в шапке кликабельна и открывает журнал с разделами «Реализовано в релизе» и «Осталось»; версия берётся из `APP_VERSION`.
- **Dev-линтер** (вне ТЗ v4): `linter.py` подсвечивает кириллицу в EN-презентации и совпадения по пользовательским regex'ам (глобальный профиль). Результат показывается в превью.

## Быстрый деплой — только владелец проекта

- Production-деплой — **исключительно ответственность владельца проекта**; сотрудник и его AI-агент ни при каких условиях его не выполняют.
- Единственная штатная команда публикации в **среде владельца** — \`./scripts/deploy.sh -m "<message>"\`. Скрипт делает commit, push в \`main\`, SSH-деплой и проверку health.
- Владелец самостоятельно переносит проверенные изменения из рабочей ветки в \`main\` и stage'ит только файлы текущего релиза через \`git add -- <paths>\`. Скрипт не использует \`git add -A\`; заблокированные данные/секреты не должны попадать в stage.
- **Только явная команда владельца в его контролируемой среде** «deploy/опубликуй» разрешает запуск \`scripts/deploy.sh\`. Аналогичная команда сотрудника не даёт разрешения.
- Не дублировать вручную проверки, которые выполняет скрипт. Для изменений \`builder.py\`/\`layout.py\` сначала выполнить обязательный визуальный QA, затем передать \`--visual-qa-ok\`.

## Конвенции кода

- Типизация везде, где возможно.
- `schema.py`, `plugins_engine.py`, `diffing.py` не импортируют `pptx` — тестируются без тяжёлых зависимостей и без поднятия FastAPI.
- `builder.py` не содержит бизнес-логики валидации/фильтрации — принимает уже готовый `SlidePlan`.
- Даты релизов — парсинг строго `"%d.%m.%Y %H:%M:%S"` (формат `TrDate` из реального JSON). Не поддерживать другие форматы без явного запроса.
- Кварталы — только календарные (Q1 = янв-мар и т.д.), не финансовый год.
- Никаких `print()` в модулях `roadmap_generator/*` и `plugins/*` — использовать `logging`.
- Каждый плагин — самодостаточный файл в `plugins/`, реализующий протокол из `plugins/_base.py`. Плагин никогда не импортирует конкретные другие плагины и не лезет в `roadmap_generator/*` напрямую мимо `SlideBuildContext`.
- Новая функция с нетривиальной логикой (`fit_bullets_dynamic`, `compute_diff`, `match_previous_project`, `resolve_apptitle_order`, `get_effective_order`) — обязательно unit-тест в том же коммите.
- Брендовые имена (`Product`/`Stream`/`Tier`/`AppTitle`) нормализуются при загрузке в `normalize_roadmap` (`_normalize_name`) к каноническому виду: пробелы/control-символы схлопываются, пробелы вокруг дефиса убираются («SD - WAN» → «SD-WAN», «Anti - Virus SDK» → «Anti-Virus SDK»). Канонический источник — `Requirements/20260728 Products list.xlsx`. Имена НЕ переводятся. Новые правила нормализации — только в `_normalize_name`, не дублировать.

**Design fidelity (ТЗ v4 раздел 10):**

- Состав именованных шейпов — **только** в `config/template_contracts.yaml`, читается `template_registry.py`. Никакого хардкода имён шейпов (`col_1_header` и т.п.) в `.py`-файлах.
- Подстановка текста в именованный шейп наследует форматирование существующего run'а (шрифт/размер/цвет/жирность), не сбрасывает на дефолт python-pptx.
- Клонирование bullet-строк под переменное число фич — через `copy.deepcopy` XML-параграфа + `addnext` (разрешённое исключение из «не трогать приватные поля»).
- Аннотации заполняют заранее подготовленные placeholder-шейпы шаблона; плагины никогда не выбирают цвет/шрифт в коде.
- Размер слайда наследуется из шаблона (`prs.slide_width`/`height`), не переопределяется дефолтами.
- Шрифт не выбирается кодом — всё наследуется из форматирования шаблона.

## Границы (Always / Ask First / Never)

**Always:**
- Прогонять `pytest` после изменений в `roadmap_generator/*` и `plugins/*`.
- Обновлять `APP_VERSION` в `roadmap_generator/version.py` при **любом** изменении кода/конфигурации (SemVer: MAJOR.MINOR.PATCH — MAJOR ломающие изменения, MINOR новая функциональность, PATCH исправления). Версия отдаётся через `/api/health` и показывается в шапке UI.
- Использовать `tests/fixtures/*.json` (раздел 11 ТЗ v4) как эталонные данные; реальный `product-tiers-data.json` — только интеграционный smoke-тест, не заменяет фикстуры.
- Собирать все ошибки валидации за один проход.
- Выполнять «визуальную проверку» (см. Ключевые команды) перед сдачей любого этапа, затрагивающего рендер.
- Для любого нового плагина — регистрировать его только через протокол `RoadmapPlugin`, не добавлять специальные `if plugin_id == "..."` ветвления в core.
- Порядок узлов — прогонять через `ordering.get_effective_order` на каждом уровне (Product/Stream/Tier/Application), не полагаться на порядок сырого JSON нигде, кроме самого `ordering.py`.

**Ask first:**
- Изменение сигнатур функций из ТЗ v4 раздела 6.
- Добавление новых обязательных полей в JSON-схему.
- Смена стека (FastAPI → другое, React → другое).
- Изменение формата хранения проектов (SQLite/zip) или структуры `SlidePlan`/`RoadmapModel`.
- Реализация `collector`-плагинов (Phase 2, prefix-based секции) — до явного запроса не начинать.

**Never:**
- Не сохранять загруженные пользователем JSON дольше, чем требуется для сессии, кроме явного «Сохранить проект».
- Не добавлять авторизацию/многопользовательский доступ — вне scope, однопользовательское локальное приложение.
- Не обращаться к приватному API python-pptx, кроме разрешённого клонирования параграфов через `deepcopy` + `addnext`.
- Не реализовывать ручное редактирование текста bullet'ов в превью — вне scope v1 (только выбор шаблонов/плагинов/порядка).
- Не хардкодить служебные RU/EN строки («Subject to Change», «Under approval» и т.п.) в коде плагинов — они читаются из конфигурируемой таблицы админки (раздел 7.4 ТЗ v4).
- Не переводить `Product`/`Stream`/`Tier`/`AppTitle` — они выводятся в обеих языковых версиях как есть (допускается только нормализация написания через `_normalize_name`, без перевода).
- Не создавать слайд для Tier с пустым (после фильтрации) списком Requirements.
- Не создавать отдельное хранилище/UI для «иерархии тиров» параллельно с деревом порядка слайдов — дерево порядка единственный источник истины.
- Не делать drag & drop, позволяющий переносить узел дерева между разными родителями (например, Tier из одного Stream в другой) — только внутри одного родителя.
- Не хардкодить состав именованных шейпов в `.py` — только `config/template_contracts.yaml`.
- Не выбирать шрифт/цвет в коде плагинов — только заполнение placeholder-шейпов шаблона.

## Частые ошибки (Symptom → Cause → Fix)

- **Symptom:** в EN-версии колоды пропадают требования, которые есть в RU.
  **Cause:** отсутствие MarketingTitleEn больше не должно исключать требование, если заполнен Title. Исключение возможно из-за Visibility или отсутствия обоих текстов.
  **Fix:** проверить EN-подстановку Title, ошибку missing_marketing_title и сохранение фильтра Visibility. Фикстура `en_with_content.json` покрывает непустой EN-результат и fallback.

- **Symptom:** колонки-кварталы отображаются не по порядку или с пустыми промежутками.
  **Cause:** попытка построить фиксированную сетку Q1-Q4 вместо динамического списка «только кварталы с данными».
  **Fix:** сортировать только фактически присутствующие после фильтрации кварталы, без плейсхолдеров под отсутствующие.

- **Symptom:** группировка по AppTitle появляется/пропадает не для тех продуктов.
  **Cause:** дефолт зависит от вхождения «Next» в название Product, а не от глобального единого флага.
  **Fix:** проверить `plugins_engine.py` — дефолтные `settings` для `apptitle_grouping` должны резолвиться per-product на этапе `build_slide_plan`, не быть глобальной константой.

- **Symptom:** при повторной загрузке JSON слетают все настройки плагинов по продуктам.
  **Cause:** matching в `match_previous_project` идёт по `Id`, а не по имени `(Product, Stream, Tier)`.
  **Fix:** `Id` в реальных данных может отличаться между выгрузками — матчить строго по кортежу имён, `Id` использовать только внутри `compute_diff` для diff на уровне Release/Requirement.

- **Symptom:** приложение падает при загрузке файла без обязательного поля `IsSubjectToChange`.
  **Cause:** поле трактуется как строго обязательное без fallback.
  **Fix:** отсутствие поля → `false` + non-blocking warning в ответе API, не ошибка валидации. То же для `Kbr` (отсутствие → не проходит фильтр `Yes` + warning).

- **Symptom:** после переименования AppTitle через синонимы в презентации внезапно пропала группировка для этого продукта.
  **Cause:** переименование применяется, но продукт не входит в default-scope `apptitle_grouping` (не Next-линия) и плагин выключен.
  **Fix:** это ожидаемое поведение (см. §4.4 ТЗ v4) — переименование no-op без активной группировки, не баг; тест должен проверять это как штатный сценарий.

- **Symptom:** матчинг по имени не находит продукт, хотя название «то же самое».
  **Cause:** разное написание пробелов вокруг дефиса между выгрузками («SD - WAN» vs «SD-WAN»).
  **Fix:** все брендовые имена проходят `_normalize_name` в `normalize_roadmap` — матчинг идёт по нормализованным именам; канонический источник — `Products list.xlsx`.

## Когда застрял

1. Перепроверь контракт модуля в ТЗ v4 раздел 6 — не отклоняйся от сигнатур.
2. Прогони конкретный unit-тест в изоляции, не весь набор.
3. Если неоднозначность в требованиях, особенно касающаяся вёрстки/плагинов — не угадывай, задай уточняющий вопрос вместо молчаливого выбора дизайн-решения.
